## Misión 1

| Problema | Capa | Patrón que lo resuelve | Por qué usar este y no otro | Cuándo no aplicarlo |
| :--- | :--- | :--- | :--- | :--- |
| Hay que copiar el código de la sesión y la bitácora en cada archivo. | Políticas transversales | Front Controller + Chain of Responsibility (Middleware / Filtros) | El Front Controller permite tener un punto de entrada común y los middleware pueden revisar la sesión y registrar la bitácora antes de llegar al trámite. No basta con un Page Controller porque terminaríamos repitiendo el mismo código en cada página. | No se usa si la validación solo pertenece a una ruta específica y no hay nada que compartir con las demás. |
| El script de pagos es un switch gigante para tarjeta, SPEI y ventanilla. | Aplicación | Strategy | Cada método de pago tiene su propia forma de funcionar, así que Strategy permite cambiar entre ellos sin llenar el código de switch. No es Adapter porque Adapter sirve para adaptar una interfaz externa, no para elegir qué método ejecutar. | Strategy sobra si solo existe una forma de pago y no se espera agregar otras. |
| El banco usa términos como “créditos” y códigos 00/01 que no coinciden con los de la universidad. | Integración | Adapter | Adapter traduce lo que entrega el banco al formato que entiende la universidad, por ejemplo convirtiendo un 00 en ACREDITADO. No es Facade porque aquí el problema principal es traducir una interfaz externa, no simplificar un sistema propio. | No hace falta si ambos sistemas ya tienen exactamente la misma interfaz y formato. |
| Las consultas SQL están dentro de la plantilla del kardex y además se repiten en otros reportes. | Datos | Repository | Repository saca las consultas SQL de las vistas y las concentra en un solo lugar para poder reutilizarlas. Así la vista se preocupa por mostrar los datos y no por consultar la base de datos. | Puede ser innecesario en un CRUD muy simple donde el ORM ya resuelve el acceso a datos sin consultas repetidas ni lógica extra. |
| Un doble clic puede cobrar dos veces y el correo está mezclado con el proceso de alta. | Aplicación / Datos / Integración | Idempotencia + Unit of Work + Transactional Outbox | La idempotencia evita procesar dos veces la misma solicitud de pago. Unit of Work permite guardar el pago y el alta local dentro de una misma transacción. Transactional Outbox guarda el evento de PagoAcreditado junto con la transacción para después enviar el correo o avisar a caja sin que un fallo en esos servicios afecte el alta. | Sería demasiado si solo hubiera una escritura local sencilla, sin riesgo de peticiones repetidas ni servicios externos que puedan fallar. |
| Si el banco o el validador de CURP se caen, también se bloquea el kardex. | Integración | Timeout + Circuit Breaker | El Timeout evita esperar para siempre y el Circuit Breaker deja de intentar llamar temporalmente a un servicio que está fallando. Así una dependencia externa no termina bloqueando funciones que no dependen de ella. | No tiene sentido para errores causados por los propios datos del usuario, como un 400, porque ahí el problema no es que el servicio esté caído. |

## Misión 2

1. Enrutador / Front Controller: El request llega primero al punto de entrada del framework, que recibe la petición y sabe a qué ruta debe enviarla. Por ejemplo, en Spring esto lo hace DispatcherServlet.
2. Middleware / Filtros: Antes de procesar el pago, la petición pasa por la cadena de filtros. Aquí se puede comprobar que el alumno tenga una sesión válida y registrar el acceso en la bitácora.
3. Controlador: El controlador recibe los datos del formulario o del POST y los pasa al servicio. Su función es conectar la petición web con la lógica, no hacer toda la lógica del pago.
4. Servicio: Se ejecuta el caso de uso registrarPago(). Aquí se coordinan las reglas del proceso y también se comprueba la idempotencia para que, si el usuario manda dos veces la misma petición, no se cobre dos veces.
5. Motor de pagos: Se utiliza Strategy para elegir la forma de pago que corresponde: tarjeta, SPEI o ventanilla. Así no necesitamos un switch gigante cada vez que se agregue otro método.
6. Integración con el banco: La estrategia correspondiente utiliza un Adapter para comunicarse con el banco y traducir sus respuestas, por ejemplo convertir su código 00 en un estado que la universidad entienda como ACREDITADO.
7. Base de datos: Se utiliza Unit of Work / una transacción para guardar de forma conjunta los cambios locales del pago y el alta de materias. Si algo falla, se hace rollback y no quedan los datos a medias.
8. Transactional Outbox: Dentro de esa misma transacción se guarda un evento como PagoAcreditado en una tabla de salida. Así el evento queda registrado aunque después falle algún servicio externo.
9. Event Consumer: Un proceso en segundo plano toma ese evento y se encarga de mandar el correo al estudiante y avisar a caja. De esta forma, si el correo falla, no se pierde el pago ni el alta de materias.
